# 《怪潮突围》完整美术资产制作与验收计划

**版本：** 1.0（生产计划；不代表资产已生成）  
**对应设计：** `01_GAME_DESIGN_CN.md`  
**视觉目标：** 精致明亮卡通场景、可辨识的角色与怪潮，未来霓虹枪火和数字升级装置。  
**项目定位：** 手机竖屏 2.5D，固定斜俯视，角色与道具为可分层、可独立放置的透明精灵。

## 1. 与概念图严格区分

**概念图（reference）：** 可用于确认色调、角色设计、道路构图、升级门外观；**不能直接作为游戏中独立敌人、动态 UI 或完整角色动作资产**。

**生产级资源（assets）：** 每一项是具有透明边缘、统一摄像机角度、合理锚点/层次/尺寸、可在游戏里单独移动与碰撞的文件。动作需要多帧或可分层部件；逻辑和数字文字由代码实现。

现有 V1 素材包包含 `highway_day.png`（静态背景）、`player_soldier_back.png`（单帧）、`fire_rate_plus_20.png`（固定文字）、`style_reference_only.png`（拼图）。**默认标为“旧版参考/待重验”，不按最终 B+C 风格计为已验收完成。** 新生成的大型展示拼图也只可作参考，不纳入可用图集。

## 2. 先锁定视觉规范（Style Bible）

| 项目 | 冻结标准 |
|---|---|
| 总体 | 明亮废土科幻 + 卡通质感，材料饱满、轮廓清晰、颜色鲜明但不过曝 |
| 场景 | 日间城市高架、蓝灰道路、少量绿植/车辆残骸；背景细节不与奖励抢视觉注意力 |
| 战斗主体 | 斜俯视（上方略向下看），角色大致向屏幕上方射击，能看到后背、头与武器 |
| 光源 | 日间左上方主光；枪火、门框和技能有独立自发光效果，但角色不能变成黑影 |
| 阵营辨识 | 玩家蓝青色、护卫绿青、重火力橙黄；敌人偏紫红/灰；可用轮廓与动作辨认，不能只依赖颜色 |
| 科技特效 | 蓝电、紫色穿透、橙色爆炸、绿色恢复、金色稀有；只在能力激活时出现 |
| 字体/UI | 清晰、紧凑、中文可读；属性数字实时绘制，不将字体烘焙进门框图片 |
| 风格禁区 | 复杂写实血腥、过暗雨夜、整张概念拼图直接使用、白底未抠图、错角度/错透视、形状漂移 |

**画面占比设计（360×800 基准）：** 道路从顶部远方收窄到底部变宽；主角大致位于下方的 75%～85% 高度，实际角色可视高度以试玩确定；中段预留 2 个并排升级门和武器箱空间；顶部 HUD 避免遮挡 Boss 技能预警。主角+4 队员+1 宠物同时存在时，道具数字仍可识别。

## 3. 生产阶段与停止条件

### P0：视觉锁定（在任何批量生图前）

交付：目标战斗图 1 张；静止四格分镜：开局、满编、战甲爆发、Boss 战；角色/怪物/门的色板和透视参考。用户明确批准**同一个画风和构图**后才继续。

验收：同屏可辨认主角、四名队员、一只宠物、怪物、数字门、武器箱；亮度清晰、不糊成霓虹海；视觉示意的镜头不要求开发成真 3D。

### P1：最小可玩美术样板（防止批量返工）

交付：一套主角（含手、腿、武器层与至少 1 套完整跑步/射击演出）、一种普通怪（移动/攻击/死亡）、一套无文字数字门、三段可无缝拼接道路、至少一种弹丸/命中效果。

验收：在临时预览中能看到角色站在道路上、独立怪物靠近，左右移动/射击的分层资源不会穿帮。**未通过禁止批量制作。**

### P2：角色和怪物全套

交付：主角 5 套武器持枪组合、队员 7 个职业/等级外观基型（突击 I/II/III、重火力 II/III、护卫 II/III）、5 类敌人、精英装饰与 1 种多阶段 Boss。

验收：同一角色跨动作不换脸、不改盔甲、不变枪；五类怪物即使缩到手机屏幕上也可凭轮廓区分，Boss 各技能具有独立可见预警。

### P3：成长和道路物件

交付：五种武器单独前景图、道具箱图、宠物 4 种三阶演出、战甲 3 套、无字动态数字门基础框和强化发光层、车/路障/运输车/救援点。

验收：数值更换不用重新生图；宠物/战甲不会错位；道具击破/拾取具有正确的独立视觉帧。

### P4：UI、粒子与音频

交付：20 词条图标、职业/宠物/战甲 HUD、技能环、三选一卡牌、结算图；枪火/弹丸/电弧/爆炸/恢复/护盾；音乐与音效，并检查资源授权。

验收：小屏可读，全部特效能在低画质档减少粒子，音频能分别静音。

### P5：整理封包与整体验收

交付：PNG 主源、优化 WebP/图集、`asset_manifest.json`、预览联系表、命名与授权信息、缺陷记录、打包脚本或明确制作流程。

验收：每个 manifest 项都指向真实文件；无透明边缘残留、无混入参考图、无重复图、无临时文件；下载包能够重建资产目录并通过完整性检查。

## 5. 统一尺寸与导出规范

| 资产 | 原始制作建议 | 发布时规范 |
|---|---|---|
| 主角/队员 | 512×512 或按角色比例单独裁边，高分辨 PNG/RGBA | 图集或 WebP，不拉伸，保持锚点 |
| 普通敌人 | 384～768 像素边长，取决于屏幕可见尺寸 | 相同角色跨动作统一边界坐标 |
| Boss | 1024×1024 或必要时更高 | 避免巨图长驻内存，分层与裁切 |
| 宠物 | 256～512 像素，RGBA | 三级进化可以共用本体+配件 |
| 战甲 | 主角身形同锚点的覆盖层，RGBA | 激活/结束与主角动作兼容 |
| 升级门 | 透明无文字门框，建议 512 或 768 像素级 | 运行时叠加中文和动态数字 |
| 道路 | 至少 1080 像素宽的主源与无缝路面切片 | 制作独立可循环层，不只一张整屏图 |
| 图标 | SVG 可用时优先保留矢量源，否则 256×256 PNG | 导出多尺寸，可读且不糊 |
| UI 背景 | 按可伸缩九宫格 / 矢量绘制 | 9:16 逻辑布局、安全边距 |

导出前检查：透明像素边缘颜色污染、白边、错误文字、多余物体、武器漂浮、角色阴影是否作为独立层、动作连续性与朝向。AI 生成的图即使宣称透明，也必须检查文件是否真的有 alpha 通道及边缘像素。

## 6. 动画技术路线（针对 AI 图的真实限制）

1. **主角和队员：** 优先分层角色（躯干/腿/两臂/武器/枪口/阴影），由代码驱动跑步摆动、轻微倾斜、射击后坐力；重要受击/倒下动作单独补关键帧。
2. **敌人：** 走动用分层或 4～8 帧循环的规范化动作图；进攻/受击与死亡至少有清晰状态差异。不能每一帧都改变脸、手臂数量或装甲形状。
3. **Boss：** 主体分部件（上身、武器、装甲）配合有限攻击姿态和特效；三种技能须有独立预警与视觉反馈。
4. **宠物：** 本体悬浮/小幅转动由程序驱动，三阶使用外观叠加，技能使用独立透明特效。
5. **战甲：** 同主角锚点的外观覆盖图层与小型变身帧序列；不能拿一张全屏概念图遮住角色。
6. **UI：** 尽量由 HTML Canvas / DOM / WebGL 绘制动态文字和条形，不靠图像中固定写死 `+20%`。

**任何生成失败或风格不一致的帧都应该标记为“返工”，不能以“已生成”代替验收。**

## 7. 文件与数据组织

推荐资源路径（仅表示将来制作后的目标结构，当前并非真实文件）：

```text
assets/
  characters/player/{body,head,arms,legs,shadow,poses}/
  characters/squad/{assault,heavy,guard}/{tier1,tier2,tier3}/
  enemies/{basic,runner,armored,ranged,elite,boss}/
  pets/{dragon,owl,shieldbot,healer}/{base,overlays,fx}/
  armor/{thunder,inferno,phantom}/{overlay,transform,fx}/
  weapons/{rifle,minigun,shotgun,plasma,laser}/
  gates/{blue,green,orange,purple}/{frame,charging,claimed}/
  items/{crates,cores,rescue,transport,obstacles}/
  world/{road_segments,parallax,props}/
  fx/{bullets,hit,fire,ice,electric,shield,healing}/
  ui/{hud,icons,trait_cards,menus}/
  audio/{music,sfx}/
  reference/
  asset_manifest.json
```

**清单最少字段：** `id`、`file`、`category`、`status`、`source`、`license_note`、`width`、`height`、`alpha`、`pivot`、`frame_count`、`fps`、`collision_hint`、`layer`、`approved`。

状态必须区分：`planned`（未做）、`generated_unreviewed`（已生图待验）、`needs_cleanup`（返工）、`approved_source`（可用原稿）、`optimized_ready`（可发布）。只允许 `optimized_ready` 资源进入正式构建，必要时添加明确的临时占位白名单。

**质量红线：** 不编造素材路径；不能把未独立拆分的概念拼图变成实际精灵；不可将图片像素中写死的数字当作动态奖励；不把普通背面立绘误称为完整动作集。

## 8. 性能和大小预算（暂定）

- Android Chrome 和 PWA 优先；目标 45～60 FPS，较弱设备 30 FPS 作为最低优化方向，具体设备需测试。
- 第一版构建建议限制纹理常驻总量，异步预加载当前阶段及下一阶段所需图集；远景压缩、小道具裁边。
- 参考运行时预算起点：屏幕内普通怪约 30～45 个、精英与 Boss 独立预算、主要弹丸逻辑对象约 80～120 个、粒子池设定可调上限；压测后调整。
- 大规模弹幕优先合并视觉轨迹与命中计算；重复音效设并发与音量限制。
- 纹理图集避免超大尺寸，一律检查手机显存占用、贴图 decode 卡顿与 PWA 缓存更新。

预算均为测试起点，不是已测得的设备能力。

## 9. 每批资源验收清单

- **美术一致性：** 透视相同、日间主光一致、角色立体质感一致、职业可辨认。
- **文件完整性：** 每个声明的资源确实存在；可打开、尺寸正确、alpha 正常，已裁切多余空白。
- **动画可用性：** 跑步/开火/受击/退场在预览中不穿帮；所有枪口锚点指向正确位置。
- **战斗可读性：** 在 360×800 的真实画面里，数字门文本、怪物轮廓、精英预警清晰。
- **性能：** 高密度怪潮同屏没有明显掉帧；特效可降级。
- **安全与授权：** 不使用血腥伤口；记录 AI 生成来源、人工编辑、第三方授权，不引入无许可素材。
- **真实交付：** 允许重新打开 ZIP 并验证每个 manifest 路径、校验大小/文件 hash、浏览 PNG 和试听音频。

## 10. 批次交付门槛

**Gate 0：** 目标游戏画面与色板获用户批准。  
**Gate 1：** 角色/怪物/门/路面 P1 最小样板实际可在手机渲染。  
**Gate 2：** P2/P3 人物、宠物、战甲和事件素材可独立使用，核心动画验收通过。  
**Gate 3：** UI、特效、音频和优化图集完整。  
**Gate 4：** 素材索引与所有文件一致，后续开发团队可直接消费，无临时拼图依赖。  

**只在 Gate 4 后进入正式 Codex 成品制作任务。** 当前未达到 Gate 0，因此该文档是制作计划，而不是交付完成声明。

## 11. 现在和下一步要做的事

1. **先做目标战斗画面作为风格定稿，而不是继续一次生成大拼图。** 需要单独确认明亮卡通角色比例、道路透视、枪火色彩、怪物密度。
2. 生成并验收一套主角可分层素材和普通怪资产，对透明背景与角色一致性作真实检查。
3. 验收后按优先级继续生产，不合格立即返工，而不是全量生成后才发现不能使用。
4. 在所有资产交付前，保持 GitHub 中旧游戏不变，不启动 Codex；最终统一打包设计文档 + 资产包 + 清单与验收要求。
