# 渲染性能记录与限制 · 2026-10-28

**性能尚未验收通过。** 只有桌面 Chromium 131、ANGLE SwiftShader 软件 WebGL，未使用安卓 GPU，也未测真机发热、耗电、触控、长局或 APK。

## 测量方法

393×873 CSS 视口、设备 DPR 1、五人队伍，注入固定敌人后冻结战斗模拟，正常浏览器帧循环继续渲染。每种配置预热 10 个回调，再采 30 个 requestAnimationFrame 间隔。它包括浏览器调度，不是独立 GPU 计时或屏幕呈现完成时间；它也不包含完整战斗模拟的开销。高档画质 0 有阴影/辉光，低档画质 2 使用 0.65 像素比例及远景 LOD。

曾尝试计时同步 renderFrame/gl.finish 调用，但几毫秒的函数耗时没有代表实际帧循环，因此**不把该数字换算为 FPS 或作为性能结果**。下表仅保留普通帧循环测量。

## 已做的针对性修正

新模式创建 WebGLRenderer 时关闭默认帧缓冲的多重采样抗锯齿，避免低档直接渲染仍承担该成本。旧模式的 antialias 保持 true，高档后处理、阴影和所有敌人均保留。该修改也意味着低画质边缘可能更明显，须在真机平衡清晰度与速度。

只对修复后的 320 敌人、低档配置进行了针对性复测；没有把修复前的其他配置冒称成修复后数据。

| 修复后场景 | 实际绘制尺寸 | 回调间隔 p50 / p95（ms） | draw calls | 提交三角形 | 保留敌人 |
| --- | --- | ---: | ---: | ---: | ---: |
| 320 敌人 / 画质 2 | 255×567 | 16.7 / 366.7 | 83 | 630,797 | 320 |

复测 WebGL 上下文确认 antialias=false，没有上下文丢失或页面错误。中位回调间隔下降，**但 p95 仍有数百毫秒的停顿，不能宣称稳定 60 FPS 或性能达标**。前后为分开的短浏览器会话，不能从这组结果推导手机帧率或通用提升倍数。原始结果见 [performance.json](evidence/performance.json)。

## 后续设备门槛

需要在至少一台中端安卓和一台较弱安卓上，运行自然开局与 160/320 怪潮、Boss、满编和战甲的实际战斗，采集持续帧间隔、GPU 时间、内存、温度与输入响应；再调整近远网格、PBR 成本、抗锯齿/分辨率、阴影和特效预算。不得以删敌人或关闭全部特效作为达标手段。

复现完整短样本：`npm run test:art-performance`。仅复现本轮修复后配置：`ART_PERF_COUNTS=320 ART_PERF_QUALITIES=2 npm run test:art-performance`。请单独运行，避免其他浏览器测试争用软件渲染资源。
